# ТЗ для Pet Project 2: Reactive Chat Service (Backpressure + Redis Pub/Sub)

## 1. Контекст и проблема
Наша SaaS-платформа использует чат клиент↔оператор как основной канал поддержки. Во время инцидентов и массовых обращений система получает всплески входящих сообщений, что приводит к задержкам доставки, росту очередей, деградации пользовательского опыта и риску обрывов активных WebSocket-сессий.

Требуется спроектировать и реализовать чат-сервис, который под нагрузкой ведет себя предсказуемо: не падает, а деградирует контролируемо за счет backpressure-механизмов, сохраняя работоспособность критичного потока сообщений.

## 2. Цель проекта
Реализовать реактивный чат-сервис для поддержки клиентов с использованием `Spring WebFlux`/`Project Reactor`, который:

- поддерживает обмен сообщениями в реальном времени через WebSocket;
- масштабируется горизонтально на несколько инстансов;
- доставляет события между инстансами через `Redis Pub/Sub`;
- демонстрирует корректную обработку перегрузки с применением backpressure-стратегий.

## 3. Функциональные требования
1. Поддержать отправку и получение сообщений в реальном времени в рамках диалогов клиент↔оператор.
2. Обеспечить работу нескольких инстансов сервиса без потери межинстансовой доставки сообщений.
3. Использовать Redis Pub/Sub для событий чата минимум по каналам:
   - `chat.message.created`
   - `chat.message.delivered`
4. Сохранять историю сообщений в MongoDB.
5. Использовать минимальную модель сообщения:
   - `messageId`
   - `chatId`
   - `senderId`
   - `type`
   - `payload`
   - `createdAt`

## 4. Требования по backpressure
1. Ограничить исходящую очередь на каждое WebSocket-соединение (`bounded buffer`).
2. При переполнении очереди применять приоритизацию и политику деградации:
   - события `typing`/прочие `ephemeral` дропать в первую очередь;
   - для критичных `chat.message` применять fail-fast для отправителя с явной ошибкой `429` / `TOO_MANY_MESSAGES`.
3. Реализовать rate limiting на пользователя (например, `N` сообщений/сек), с возможностью настройки порогов.
4. Собирать и публиковать метрики backpressure:
   - текущий размер буферов;
   - число дропнутых сообщений;
   - reject-rate;
   - latency доставки (`p95`, `p99`).

## 5. Нефункциональные требования и SLA
1. Поддержка не менее `5 000` одновременных WebSocket-подключений на тестовом стенде.
2. При штатной нагрузке задержка доставки сообщений: `p95 < 250 ms`.
3. При burst-нагрузке сервис не должен аварийно завершаться (в т.ч. OOM); ожидается контролируемая деградация.
4. Потеря критичных `chat.message` из-за backpressure недопустима в рамках активного соединения, кроме случаев, когда сообщение было явно отклонено политикой (`TOO_MANY_MESSAGES`).

## 6. Критерии приемки
1. Нагрузочный burst-сценарий подтверждает стабильность сервиса:
   - нет OOM;
   - нет лавинообразного роста latency;
   - деградация соответствует заданным политикам.
2. Демонстрируется multi-instance сценарий:
   - сообщение отправляется через инстанс `A`;
   - сообщение доставляется получателю, подключенному к инстансу `B`, через Redis Pub/Sub.
3. Доступен дашборд или лог-отчет с ключевыми backpressure-метриками.
4. Интеграционные тесты покрывают сценарии:
   - нормальный поток;
   - burst;
   - overflow;
   - reconnect.

## 7. Артефакты для портфолио
1. Краткая архитектурная схема потока:
   `Client -> WebFlux -> Reactor -> Redis Pub/Sub -> WebSocket sessions`.
2. Таблица сравнения метрик под нагрузкой в формате “до/после”.
3. Раздел `Trade-offs`:
   - почему выбран Redis Pub/Sub;
   - ограничения Redis Pub/Sub в данном контексте;
   - план эволюции решения при росте требований.

## 8. Public Interfaces / Contracts
В реализации обязательно зафиксировать и документировать:

1. WebSocket endpoint для чата (единая точка входа для realtime-коммуникации).
2. Конвенцию именования Redis-каналов для событий чата.
3. Единый JSON envelope для событий/сообщений (минимум: метаданные события, тип, payload, timestamp).
4. Явные коды ошибок для throttling/backpressure, включая `TOO_MANY_MESSAGES`.

## 9. Test Plan
1. Unit-тесты backpressure-логики:
   - поведение при переполнении буфера;
   - корректный drop/reject по типу события.
2. Интеграционные тесты Redis Pub/Sub между двумя инстансами.
3. Нагрузочный тест burst-сценария с проверкой SLA и метрик.
4. Негативные тесты:
   - медленный consumer;
   - reconnect;
   - превышение rate limit.
